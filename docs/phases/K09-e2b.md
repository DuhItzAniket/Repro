## Objective
ADR-0018's option B, accepted by the owner on 2026-10-19: a sandbox of its own,
`E2BSandbox`, with each side of a run in a Firecracker microVM of a self-hosted E2B, at L5.
The owner asked for it on 2026-10-22, and approved installing E2B's self-hosted stack (Embed)
in WSL2 for it.

## Scope
- **`sandbox = "e2b"`** (`REPRO_SANDBOX`), the VM's size as `e2b_memory_mb` and `e2b_cpus`.
  E2B is reached as its SDK says (`E2B_API_KEY`, `E2B_API_URL`): Repro holds no E2B key.
- **`RemoteSandbox`:** what the runners need of a sandbox whose snapshot is elsewhere. Docker's
  and E2B's both provide it, so pytest, probes and the sides' helpers run unchanged on either.
- **`E2BSandbox`:**
  - the template is Repro's image recipe, step by step, with nftables and a user `repro`
    (uid 1001, no sudo), named by the recipe's digest and size and built once per E2B;
  - the snapshot and the hook go in as archives (the hook read-only);
  - **the seal** comes before any of the target's code runs. Root adds an nftables rule to
    the VM's own kernel that rejects every packet `repro` sends, but to loopback, and E2B is
    asked to deny every address too. A probe as `repro` must then fail to reach the index by
    name and two addresses by number, or the side has no sandbox;
  - `run` refuses an unsealed VM. Commands run as `repro` under its process limit, and are
    killed at their timeout;
  - the VM's lifetime is renewed while it works, since E2B allows an hour at most.
- **`E2BProvisioner`:** dependencies from wheels (`--no-build`) before the seal, then the
  project offline after it.
- **The schema:** `e2b` as a sandbox backend in `run.started`.
- **Packaging:** E2B's SDK (`e2b` 2.46.0, MIT) as the `e2b` extra. Its dependencies are MIT,
  Apache-2.0 or BSD; `protobuf-py-ext`, which names no licence in its wheels, is an exception
  with its source repository's licence (Apache-2.0).
- **CI:** a job `e2b` that starts Embed from a pinned commit on GitHub's runner and runs the
  live tests. It is not required.
- **Docs:** ADR-0018's B as built, ARCHITECTURE §8, THREAT_MODEL T1 and T2, the settings,
  CONTRIBUTING and TEST_STRATEGY.

## Out of scope
- JavaScript on E2B: a JavaScript change with `sandbox = e2b` gets a missing item, never a
  weaker sandbox in its place.
- E2B Cloud: K09 targets the self-hosted stack, and E2B Cloud would need an account and key.
- A cache of environments across runs: each side installs its dependencies afresh.

## Acceptance criteria
- [x] AC1: a side runs in a microVM from a template of Repro's image, at L5.
- [x] AC2: nothing of the target's runs before the network is closed and checked from inside;
  a seal that does not hold gives no sandbox.
- [x] AC3: the target's code runs as a user that cannot reopen the network.
- [x] AC4: a run end to end gives the fixture's evidence, a card at L5 and `run.started`'s
  backend `e2b`.
- [x] AC5: the process limit and timeouts hold.

## Evidence
Measured on the owner's machine on 2026-10-22 and 23: WSL 3.0.3 (kernel 6.18.54), Ubuntu
24.04, Docker 29.8.2, and E2B Embed at `e2b-dev/runtime` commit `c92e06b`, its files checked by
SHA-256. WSL2 has 7.6 GB, so E2B's memory pool was set to 2 GB (`HUGEPAGES=1024`) and the
microVMs to 512 MB.

**Getting there:**
- Embed refused WSL 2.6's kernel 6.6 ("older than 6.8"). The owner updated WSL to 3.0.3, and
  its preflight then passed.
- E2B's builder refused Repro's Dockerfile: its `COPY --from` reads `/uv`, and "absolute paths
  are not allowed". So the template is built in steps.
- A 1 GB template ran E2B's builder out of memory ("mmap memfd: cannot allocate memory"), so
  512 MB is used here.
- E2B refused a 4-hour lifetime ("Timeout cannot be greater than 1 hours"), so the lifetime is
  an hour, renewed while the VM works.
- WSL 3 stops its VM when no session is open, which restarted E2B between commands. A
  long-lived WSL session keeps it up.

**E2B's own firewall.** One VM per way of asking E2B to deny all traffic: no rules, then
`update_network` deny; `allow_internet_access=False`; `deny_out` all; `allow_out` the index
with `deny_out` all.
- **Names:** in every case that denied, names no longer resolved and DNS over UDP timed out.
- **Numbered addresses:** in every case, TCP to `1.1.1.1:443`, `8.8.8.8:443` and `1.1.1.1:53`
  connected. With the index allowed, `example.com:80` connected too.
- **The guest's own rule:** with the nftables rule in the guest (kernel 6.1.177, which has
  nf_tables but not iptables' owner match), every one of these was refused for uid 1001.
  E2B's agent, which runs as root, kept working.

**The microVM, by hand:**
- the template built in 23 s;
- a VM started with its hook and snapshot in 0.3 s, and the seal was set and checked in 0.1 s;
- commands ran as `repro`, with uv 0.13.0 and Python 3.13.11;
- `sudo` was refused;
- a fork bomb met "Cannot fork" at 64 processes, and a timeout killed its command at 3.1 s;
- a network attempt was refused and recorded by Repro's hook.

**The tests in WSL2:** the 19 E2B tests passed in 33 s, the end-to-end run in 20 s. The Docker
module passed with `RemoteSandbox` (25 passed, 1 skipped).

**CI's `e2b` job** (run 39845175284, GitHub's `ubuntu-24.04`, 1 GB microVMs):
- E2B Embed started from the pinned files;
- the 5 live tests and the end-to-end run passed in 59 s;
- the job took 3 minutes.

Getting it there took three fixes to the job, none to the sandbox:
- the workflow file was first written through a shell that collapsed its line continuations;
- `compose.yaml`'s SHA-256 had lost a digit in transcription;
- the job loaded `nbd` itself, with modprobe's default of 16 devices, and E2B's host-setup,
  which asks for 64 and stops when it finds fewer, refused. The job now only checks that the
  module is there.

## Deviations from spec
- **The network is the guest kernel's.** ADR-0018 B said E2B's egress firewall would deny
  everything. Measured, it did not, so the seal is the VM's own firewall, checked from inside,
  with E2B's kept as a second layer.
- **Commands run as Repro's own user.** E2B's `user` has sudo, so the target runs as `repro`.
- **The template is built from steps,** not from the Dockerfile.

## Known gaps
- **A guest kernel exploit.** It would make the target root in its VM, able to remove the
  guest's rule. E2B's own firewall would then be the only layer, and K09 measured it letting
  numbered addresses through on WSL2. The VM boundary (L5) still holds for the host.
- **No cache.** Each side installs its dependencies afresh: slower than Docker's cached
  environments.
- **Memory.** On WSL2 with 7.6 GB, microVMs are 512 MB, and a test suite needing more is
  killed at that limit. A host with more memory raises `e2b_memory_mb`.
- **No JavaScript.** JavaScript changes are not supported on E2B (Out of scope).
- **Not yet compared with Docker.** The live trial ran one fixture end to end. A comparison of
  run times with Docker's sandbox on real projects was not made.

## Dependencies added
- `e2b` 2.46.0 (MIT), as the optional `e2b` extra, with its dependencies (MIT, Apache-2.0,
  BSD). It is not installed unless asked for.
- On the host: E2B Embed (Apache-2.0), installed by its own compose guide, not by Repro.
